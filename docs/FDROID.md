# Hexsweeper on F-Droid

Hexsweeper is not in the F-Droid catalog. This page records what a catalog
build is, how to make one, and what is still open before a request can be
filed. The recipe draft is
[fdroid/metadata/app.hexodus.ios.yml](../fdroid/metadata/app.hexodus.ios.yml).

## What F-Droid would build

The Android app under `app/`: a Capacitor shell around a sealed Sphere
payload. The F-Droid build uses `app/www-fdroid/` instead of `app/www/`. It is
the same game without two things that are not under an open license:

- the Galaxy, Heat Lightning and Ion Storm themes, which reflect photographs
  under the Unsplash License. The Themes tab shows Light, Dark, Mercury and
  Aurora. A saved choice of a removed theme falls back to Light.
- the screenshot of Microsoft Minesweeper in Help.

Every other channel keeps both. The image files stay in the repository for
the web game and the direct download.

- Application id `app.hexodus.ios`, version from `app/android/app/build.gradle`.
- No permissions beyond what the launcher needs. The app declares no
  `INTERNET` permission and the payload makes no network requests.
- No Google Play Services, Firebase, analytics or advertising code. The
  dependencies are Capacitor (MIT) from npm and AndroidX from Google's Maven
  repository and Maven Central.
- No native code. The one checked-in binary is the Gradle wrapper.
- The payload is this project's own JavaScript, generated by
  `python3 tools/export-collection.py --app` from the commit recorded in
  `app/WWW_SOURCE_FDROID.txt`, with IBM Plex (SIL Open Font License 1.1) as
  its only bundled third-party file. CI checks the payload against the
  recorded checksums and fails if the APK carries a photograph or the
  screenshot.

## Build it the way F-Droid does

JDK 21, Android SDK platform 36 and build-tools 36.0.0, Node.js and pnpm
10.18.0.

```sh
cd app
pnpm install --frozen-lockfile
scripts/android-build.sh assembleFdroidRelease
```

That sets `HEXSWEEPER_FDROID=1` (so Capacitor stages `www-fdroid/`), runs
`pnpm exec cap sync android` and then Gradle's `assembleRelease`.

Without the four `HEXSWEEPER_ANDROID_*` signing variables the result is
`android/app/build/outputs/apk/release/app-release-unsigned.apk`. The release
build leaves out the version-control file and the dependency metadata block,
so its bytes do not depend on how the source was checked out. CI runs this
build on every push and prints the file's SHA-256.

For F-Droid's reproducible-build check, sign that same unsigned file with the
Hexsweeper release key using `fdroid/sign-upstream.sh` and attach it to the
GitHub release as `hexsweeper-<version>.apk`. F-Droid rebuilds from the tag, compares, and ships
the signed file.

## Licenses

The code and the project's own artwork are MIT (`LICENSE`). Bundled
third-party material is listed in `THIRD-PARTY-NOTICES.md` and
`app/THIRD-PARTY-NOTICES.md`, and inside the app on its Licenses page.

The F-Droid build carries nothing outside those licenses, so no Anti-Feature
label applies. The repository still holds the photographs and the screenshot
for the other builds; `THIRD-PARTY-NOTICES.md` says what they are.

## Open before a request

1. The repository must be public. F-Droid clones it without signing in, and
   reviewers read its history for at least three months of development.
2. Versions 1.0.12 (37) and 1.0.13 (38) are the F-Droid build's alone: the F-Droid APK and the
   direct download share an application id and signing key, so one code must
   never name two different files. 1.0.14 (39) is the direct, Google Play and
   Amazon build of November 16, so the next F-Droid build takes 40 or higher.
   F-Droid reads the version from `app/android/app/build.gradle` as written,
   so the commit that sets 39 must not carry a `v` tag.
3. Done for 1.0.13: tag `v1.0.13`, with the signed file on its GitHub release.
   (`v1.0.12` is the same app; its listing still had a screenshot of a theme
   the F-Droid build does not include, and F-Droid reads the listing from
   the commit it builds.)
   For a later version, tag the release commit `v<version>`, publish the
   signed file the same way and update the recipe's `commit`.
4. Done on November 16, 2026, for 1.0.13 (38): the recipe is on branch `app.hexodus.ios` of
   the `fdroiddata` fork and its pipeline passes, including the build, the
   source scan and the comparison with the signed file. Two things that run
   settled: the Capacitor CLI needs Node.js 22, which Debian does not have,
   so the recipe downloads it with a checksum check; and the scanner rejects
   the template archives inside the CLI package, so the recipe deletes them
   after the sync.
5. No merge request has been opened.
